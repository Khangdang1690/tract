<p>
<b>
Erlang
</b>
(
<span>
<span>
<a>
/
<span>
<span>
ˈ
</span>
<span>
ɜːr
</span>
<span>
l
</span>
<span>
æ
</span>
<span>
ŋ
</span>
</span>
/
</a>
</span>
</span>
<a>
<i>
<span>
UR
</span>
-lang
</i>
</a>
) is a
<a>
general-purpose
</a>
,
<a>
concurrent
</a>
,
<a>
functional
</a>
<a>
high-level
</a>
<a>
programming language
</a>
, and a
<a>
garbage-collected
</a>
<a>
runtime system
</a>
. The term Erlang is used interchangeably with Erlang/OTP, or
<a>
Open Telecom Platform
</a>
(OTP), which consists of the Erlang
<a>
runtime system
</a>
, several ready-to-use components (OTP) mainly written in Erlang, and a set of
<a>
design principles
</a>
for Erlang programs.
<sup>
<a>
<span>
[
</span>
5
<span>
]
</span>
</a>
</sup>
</p>
<p>
The Erlang
<a>
runtime system
</a>
is designed for systems with these traits:
</p>
<ul>
<li>
<a>
Distributed
</a>
</li>
<li>
<a>
Fault-tolerant
</a>
</li>
<li>
<a>
Soft real-time
</a>
</li>
<li>
<a>
Highly available
</a>
,
<a>
non-stop
</a>
applications
</li>
<li>
<a>
Hot swapping
</a>
, where code can be changed without stopping a system.
<sup>
<a>
<span>
[
</span>
6
<span>
]
</span>
</a>
</sup>
</li>
</ul>
<p>
The Erlang
<a>
programming language
</a>
has data,
<a>
pattern matching
</a>
, and
<a>
functional programming
</a>
.
<sup>
<a>
<span>
[
</span>
7
<span>
]
</span>
</a>
</sup>
The sequential subset of the Erlang language supports
<a>
eager evaluation
</a>
,
<a>
single assignment
</a>
, and
<a>
dynamic typing
</a>
.
</p>
<p>
A normal Erlang application is built out of hundreds of small Erlang processes.
</p>
<p>
It was originally
<a>
proprietary software
</a>
within
<a>
Ericsson
</a>
, developed by
<a>
Joe Armstrong
</a>
, Robert Virding, and Mike Williams in 1986,
<sup>
<a>
<span>
[
</span>
8
<span>
]
</span>
</a>
</sup>
but was released as
<a>
free and open-source software
</a>
in 1998.
<sup>
<a>
<span>
[
</span>
9
<span>
]
</span>
</a>
</sup>
<sup>
<a>
<span>
[
</span>
10
<span>
]
</span>
</a>
</sup>
Erlang/OTP is supported and maintained by the Open Telecom Platform (OTP) product unit at
<a>
Ericsson
</a>
.
</p>

<div>
<h2>
History
</h2>
<span>
<span>
[
</span>
<a>
<span>
edit
</span>
</a>
<span>
]
</span>
</span>
</div>
<p>
The name
<i>
Erlang
</i>
, attributed to Bjarne Däcker, has been presumed by those working on the telephony switches (for whom the language was designed) to be a reference to Danish mathematician and engineer
<a>
Agner Krarup Erlang
</a>
and a
<a>
syllabic abbreviation
</a>
of "Ericsson Language".
<sup>
<a>
<span>
[
</span>
8
<span>
]
</span>
</a>
</sup>
<sup>
<a>
<span>
[
</span>
11
<span>
]
</span>
</a>
</sup>
<sup>
<a>
<span>
[
</span>
12
<span>
]
</span>
</a>
</sup>
Erlang was designed with the aim of improving the development of telephony applications.
<sup>
<a>
<span>
[
</span>
13
<span>
]
</span>
</a>
</sup>
The initial version of Erlang was implemented in
<a>
Prolog
</a>
and was influenced by the programming language
<a>
PLEX
</a>
used in earlier Ericsson exchanges. By 1988 Erlang had proven that it was suitable for prototyping telephone exchanges, but the Prolog interpreter was far too slow. One group within Ericsson estimated that it would need to be 40 times faster to be suitable for production use. In 1992, work began on the
<a>
BEAM
</a>
<a>
virtual machine
</a>
(VM), which compiles Erlang to C using a mix of natively compiled code and
<a>
threaded code
</a>
to strike a balance between performance and disk space.
<sup>
<a>
<span>
[
</span>
14
<span>
]
</span>
</a>
</sup>
According to co-inventor Joe Armstrong, the language went from laboratory product to real applications following the collapse of the next-generation
<a>
AXE telephone exchange
</a>
named
<a>
<i>
AXE-N
</i>
</a>
in 1995. As a result, Erlang was chosen for the next
<a>
Asynchronous Transfer Mode
</a>
(ATM) exchange
<i>
AXD
</i>
.
<sup>
<a>
<span>
[
</span>
8
<span>
]
</span>
</a>
</sup>
</p>
<figure>
<a>
<img>
</a>
<figcaption>
Robert Virding and Joe Armstrong, 2013
</figcaption>
</figure>
<p>
In February 1998, Ericsson Radio Systems banned the in-house use of Erlang for new products, citing a preference for non-proprietary languages.
<sup>
<a>
<span>
[
</span>
15
<span>
]
</span>
</a>
</sup>
The ban caused Armstrong and others to make plans to leave Ericsson.
<sup>
<a>
<span>
[
</span>
16
<span>
]
</span>
</a>
</sup>
In March 1998 Ericsson announced the AXD301 switch,
<sup>
<a>
<span>
[
</span>
8
<span>
]
</span>
</a>
</sup>
containing over a million lines of Erlang and reported to achieve a
<a>
high availability
</a>
of
<a>
nine "9"s
</a>
.
<sup>
<a>
<span>
[
</span>
17
<span>
]
</span>
</a>
</sup>
In December 1998, the implementation of Erlang was open-sourced and most of the Erlang team resigned to form a new company, Bluetail AB.
<sup>
<a>
<span>
[
</span>
8
<span>
]
</span>
</a>
</sup>
Ericsson eventually relaxed the ban and re-hired Armstrong in 2004.
<sup>
<a>
<span>
[
</span>
16
<span>
]
</span>
</a>
</sup>
</p>
<p>
In 2006, native
<a>
symmetric multiprocessing
</a>
support was added to the runtime system and VM.
<sup>
<a>
<span>
[
</span>
8
<span>
]
</span>
</a>
</sup>
</p>
<div>
<h3>
Processes
</h3>
<span>
<span>
[
</span>
<a>
<span>
edit
</span>
</a>
<span>
]
</span>
</span>
</div>
<p>
Erlang applications are built of very lightweight Erlang processes in the Erlang runtime system. The Erlang runtime system provides strict
<a>
process isolation
</a>
between Erlang processes (this includes data and garbage collection, separated individually by each Erlang process) and transparent communication between processes (see
<a>
Location transparency
</a>
) on different Erlang nodes (on different hosts).
</p>
<p>
Joe Armstrong, co-inventor of Erlang, summarized the principles of processes in his PhD thesis:
<sup>
<a>
<span>
[
</span>
18
<span>
]
</span>
</a>
</sup>
</p>
<ul>
<li>
Everything is a process.
</li>
<li>
Processes are strongly isolated.
</li>
<li>
Process creation and destruction is a lightweight operation.
</li>
<li>
Message passing is the only way for processes to interact.
</li>
<li>
Processes have unique names.
</li>
<li>
If you know the name of a process you can send it a message.
</li>
<li>
Processes share no resources.
</li>
<li>
Error handling is non-local.
</li>
<li>
Processes do what they are supposed to do or fail.
</li>
</ul>
<p>
Joe Armstrong remarked in an interview with Rackspace in 2013: "If
<a>
Java
</a>
is '
<a>
write once, run anywhere
</a>
', then Erlang is 'write once, run forever'."
<sup>
<a>
<span>
[
</span>
19
<span>
]
</span>
</a>
</sup>
</p>
<div>
<h3>
Usage
</h3>
<span>
<span>
[
</span>
<a>
<span>
edit
</span>
</a>
<span>
]
</span>
</span>
</div>
<p>
In 2014,
<a>
Ericsson
</a>
reported Erlang was being used in its support nodes, and in
<a>
GPRS
</a>
,
<a>
3G
</a>
and
<a>
LTE
</a>
mobile networks worldwide and also by
<a>
Nortel
</a>
and
<a>
Deutsche Telekom
</a>
.
<sup>
<a>
<span>
[
</span>
20
<span>
]
</span>
</a>
</sup>
</p>
<p>
Erlang is used in
<a>
RabbitMQ
</a>
. As
<a>
Tim Bray
</a>
, director of Web Technologies at
<a>
Sun Microsystems
</a>
, expressed in his keynote at
<a>
O'Reilly Open Source Convention
</a>
(OSCON) in July 2008:
</p>
<blockquote>
<p>
If somebody came to me and wanted to pay me a lot of money to build a large scale message handling system that really had to be up all the time, could never afford to go down for years at a time, I would unhesitatingly choose Erlang to build it in.
</p>
</blockquote>
<p>
Erlang is the programming language used to code
<a>
WhatsApp
</a>
.
<sup>
<a>
<span>
[
</span>
21
<span>
]
</span>
</a>
</sup>
</p>
<p>
It is also the language of choice for
<a>
Ejabberd
</a>
– an
<a>
XMPP
</a>
messaging server.
</p>
<p>
<a>
Elixir
</a>
is a programming language that compiles into BEAM byte code (via Erlang Abstract Format).
<sup>
<a>
<span>
[
</span>
22
<span>
]
</span>
</a>
</sup>
</p>
<p>
Since being released as open source, Erlang has been spreading beyond telecoms, establishing itself in other vertical markets such as FinTech, gaming, healthcare, automotive,
<a>
Internet of Things
</a>
and blockchain. Apart from WhatsApp, there are other companies listed as Erlang's success stories, including
<a>
Vocalink
</a>
(a MasterCard company),
<a>
Goldman Sachs
</a>
,
<a>
Nintendo
</a>
, AdRoll,
<a>
Grindr
</a>
,
<a>
BT Mobile
</a>
,
<a>
Samsung
</a>
,
<a>
OpenX
</a>
, and
<a>
SITA
</a>
.
<sup>
<a>
<span>
[
</span>
23
<span>
]
</span>
</a>
</sup>
<sup>
<a>
<span>
[
</span>
24
<span>
]
</span>
</a>
</sup>
</p>

<div>
<h3>
Fibonacci sequence
</h3>
<span>
<span>
[
</span>
<a>
<span>
edit
</span>
</a>
<span>
]
</span>
</span>
</div>
<p>
A tail recursive algorithm that produces the
<a>
Fibonacci sequence
</a>
:
</p>
<div>
<pre>
<span>
</span>
<span>
%% The module declaration must match the file name "series.erl"
</span>
<span>
-
</span>
<span>
module
</span>
<span>
(
</span>
<span>
series
</span>
<span>
).
</span>
<span>
%% The export statement contains a list of all those functions that form
</span>
<span>
%% the module's public API. In this case, this module exposes a single
</span>
<span>
%% function called fib that takes 1 argument (I.E. has an arity of 1)
</span>
<span>
%% The general syntax for -export is a list containing the name and
</span>
<span>
%% arity of each public function
</span>
<span>
-
</span>
<span>
export
</span>
<span>
([
</span>
<span>
fib
</span>
<span>
/
</span>
<span>
1
</span>
<span>
]).
</span>
<span>
%% ---------------------------------------------------------------------
</span>
<span>
%% Public API
</span>
<span>
%% ---------------------------------------------------------------------
</span>
<span>
%% Handle cases in which fib/1 receives specific values
</span>
<span>
%% The order in which these function signatures are declared is a vital
</span>
<span>
%% part of this module's functionality
</span>
<span>
%% If fib/1 receives a negative number, then return the atom err_neg_val
</span>
<span>
%% Normally, such defensive coding is discouraged due to Erlang's 'Let
</span>
<span>
%% it Crash' philosophy, but here the result would be an infinite loop.
</span>
<span>
fib
</span>
<span>
(
</span>
<span>
N
</span>
<span>
)
</span>
<span>
</span>
<span>
when
</span>
<span>
</span>
<span>
N
</span>
<span>
</span>
<span>
<
</span>
<span>
</span>
<span>
0
</span>
<span>
</span>
<span>
->
</span>
<span>
</span>
<span>
err_neg_val
</span>
<span>
;
</span>
<span>
%% If fib/1 is passed precisely the integer 0, then return 0
</span>
<span>
fib
</span>
<span>
(
</span>
<span>
0
</span>
<span>
)
</span>
<span>
</span>
<span>
->
</span>
<span>
</span>
<span>
0
</span>
<span>
;
</span>
<span>
%% For all other values, call the private function fib_int/3 to perform
</span>
<span>
%% the calculation
</span>
<span>
fib
</span>
<span>
(
</span>
<span>
N
</span>
<span>
)
</span>
<span>
</span>
<span>
->
</span>
<span>

<div>
<h2>
Data types
</h2>
<span>
<span>
[
</span>
<a>
<span>
edit
</span>
</a>
<span>
]
</span>
</span>
</div>
<p>
Erlang has eight primitive
<a>
data types
</a>
:
</p>
<dl>
<dt>
Integers
</dt>
<dd>
Integers are written as sequences of decimal digits, for example, 12, 12375 and -23427 are integers. Integer arithmetic is exact and only limited by available memory on the machine. (This is called
<a>
arbitrary-precision arithmetic
</a>
.)
</dd>
<dt>
Atoms
</dt>
<dd>
Atoms are used within a program to denote distinguished values. They are written as strings of consecutive alphanumeric characters, the first character being lowercase. Atoms can contain any character if they are enclosed within single quotes and an escape convention exists which allows any character to be used within an atom. Atoms are never garbage collected and should be used with caution, especially if using dynamic atom generation.
</dd>
<dt>
Floats
</dt>
<dd>
Floating point numbers use the
<a>
IEEE 754 64-bit representation
</a>
.
</dd>
<dt>
References
</dt>
<dd>
References are globally unique symbols whose only property is that they can be compared for equality. They are created by evaluating the Erlang primitive
<code>
make_ref()
</code>
.
</dd>
<dt>
Binaries
</dt>
<dd>
A binary is a sequence of bytes. Binaries provide a space-efficient way of storing binary data. Erlang primitives exist for composing and decomposing binaries and for efficient input/output of binaries.
</dd>
<dt>
Pids
</dt>
<dd>
Pid is short for
<i>
process identifier
</i>
– a Pid is created by the Erlang primitive
<code>
spawn(...)
</code>
Pids are references to Erlang processes.
</dd>
<dt>
Ports
</dt>
<dd>
Ports are used to communicate with the external world. Ports are created with the built-in function
<code>
open_port
</code>
. Messages can be sent to and received from ports, but these messages must obey the so-called "port protocol."
</dd>
<dt>
Funs
</dt>
<dd>
Funs are function
<a>
closures
</a>
. Funs are created by expressions of the form:
<code>
fun(...) -> ... end
</code>
.
</dd>
</dl>
<p>
And three compound data types:
</p>
<dl>
<dt>
Tuples
</dt>
<dd>
Tuples are containers for a fixed number of Erlang data types. The syntax
<code>
{D1,D2,...,Dn}
</code>
denotes a tuple whose arguments are
<code>
D1, D2, ... Dn.
</code>
The arguments can be primitive data types or compound data types. Any element of a tuple can be accessed in constant time.
</dd>
<dt>
Lists
</dt>
<dd>
Lists are containers for a variable number of Erlang data types. The syntax
<code>
[Dh|Dt]
</code>
denotes a list whose first element is
<code>
Dh
</code>
, and whose remaining elements are the list
<code>
Dt
</code>
. The syntax
<code>
[]
</code>
denotes an empty list. The syntax
<code>
[D1,D2,..,Dn]
</code>
is short for
<code>
[D1|[D2|..|[Dn|[]]]]
</code>
. The first element of a list can be accessed in constant time. The first element of a list is called the
<i>
head
</i>
of the list. The remainder of a list when its head has been removed is called the
<i>
tail
</i>
of the list.
</dd>
<dt>
Maps
</dt>
<dd>
Maps contain a variable number of key-value associations. The syntax is
<code>
#{Key1=>Value1,...,KeyN=>ValueN}
</code>
.
</dd>
</dl>
<p>
Two forms of
<a>
syntactic sugar
</a>
are provided:
</p>
<dl>
<dt>
Strings
</dt>
<dd>
Strings are written as doubly quoted lists of characters. This is syntactic sugar for a list of the integer
<a>
Unicode
</a>
code points for the characters in the string. Thus, for example, the string "cat" is shorthand for
<code>
[99,97,116]
</code>
.
<sup>
<a>
<span>
[
</span>
26
<span>
]
</span>
</a>
</sup>
</dd>
<dt>
Records
</dt>
<dd>
Records provide a convenient way for associating a tag with each of the elements in a tuple. This allows one to refer to an element of a tuple by name and not by position. A pre-compiler takes the record definition and replaces it with the appropriate tuple reference.
</dd>
</dl>
<div>
<h2>
<span>
</span>
"Let it crash" coding style
</h2>
<span>
<span>
[
</span>
<a>
<span>
edit
</span>
</a>
<span>
]
</span>
</span>
</div>
<p>
Erlang is designed with a mechanism that makes it easy for external processes to monitor for crashes (or hardware failures), rather than an in-process mechanism like
<a>
exception handling
</a>
used in many other programming languages. Crashes are reported like other messages, which is the only way processes can communicate with each other,
<sup>
<a>
<span>
[
</span>
27
<span>
]
</span>
</a>
</sup>
and subprocesses can be spawned cheaply (see
<a>
below
</a>
). The "let it crash" philosophy prefers that a process be completely restarted rather than trying to recover from a serious failure.
<sup>
<a>
<span>
[
</span>
28
<span>
]
</span>
</a>
</sup>
Though it still requires handling of errors, this philosophy results in less code devoted to
<a>
defensive programming
</a>
where error-handling code is highly contextual and specific.
<sup>
<a>
<span>
[
</span>
27
<span>
]
</span>
</a>
</sup>
</p>
<div>
<h3>
Supervisor trees
</h3>
<span>
<span>
[
</span>
<a>
<span>
edit
</span>
</a>
<span>
]
</span>
</span>
</div>
<p>
A typical Erlang application is written in the form of a supervisor tree. This architecture is based on a hierarchy of processes in which the top level process is known as a "supervisor". The supervisor then spawns multiple child processes that act either as workers or more, lower level supervisors. Such hierarchies can exist to arbitrary depths and have proven to provide a highly scalable and fault-tolerant environment within which application functionality can be implemented.
</p>
<p>
Within a supervisor tree, all supervisor processes are responsible for managing the lifecycle of their child processes, and this includes handling situations in which those child processes crash. Any process can become a supervisor by first spawning a child process, then calling
<code>
erlang:monitor/2
</code>
on that process. If the monitored process then crashes, the supervisor will receive a message containing a tuple whose first member is the atom
<code>
'DOWN'
</code>
. The supervisor is responsible firstly for listening for such messages and for taking the appropriate action to correct the error condition.
</p>
<div>
<h2>
Concurrency and distribution orientation
</h2>
<span>
<span>
[
</span>
<a>
<span>
edit
</span>
</a>
<span>
]
</span>
</span>
</div>
<p>
Erlang's main strength is support for
<a>
concurrency
</a>
. It has a small but powerful set of primitives to create processes and communicate among them. Erlang is conceptually similar to the language
<a>
occam
</a>
, though it recasts the ideas of
<a>
communicating sequential processes
</a>
(CSP) in a functional framework and uses asynchronous message passing.
<sup>
<a>
<span>
[
</span>
29
<span>
]
</span>
</a>
</sup>
Processes are the primary means to structure an Erlang application. They are neither
<a>
operating system
</a>
<a>
processes
</a>
nor
<a>
threads
</a>
, but
<a>
lightweight processes
</a>
that are scheduled by BEAM. Like operating system processes (but unlike operating system threads), they share no state with each other. The estimated minimal overhead for each is 300
<a>
words
</a>
.
<sup>
<a>
<span>
[
</span>
30
<span>
]
</span>
</a>
</sup>
Thus, many processes can be created without degrading performance. In 2005, a benchmark with 20 million processes was successfully performed with 64-bit Erlang on a machine with 16 GB
<a>
random-access memory
</a>
(RAM; total 800 bytes/process).
<sup>
<a>
<span>
[
</span>
31
<span>
]
</span>
</a>
</sup>
Erlang has supported
<a>
symmetric multiprocessing
</a>
since release R11B of May 2006.
</p>
<p>
While
<a>
threads
</a>
need external library support in most languages, Erlang provides language-level features to create and manage processes with the goal of simplifying concurrent programming. Though all concurrency is explicit in Erlang, processes communicate using
<a>
message passing
</a>
instead of shared variables, which removes the need for explicit
<a>
locks
</a>
(a locking scheme is still used internally by the VM).
<sup>
<a>
<span>
[
</span>
32
<span>
]
</span>
</a>
</sup>
</p>
<p>
<a>
Inter-process communication
</a>
works via a
<a>
shared-nothing
</a>
<a>
asynchronous
</a>
<a>
message passing
</a>
system: every process has a "mailbox", a
<a>
queue
</a>
of messages that have been sent by other processes and not yet consumed. A process uses the
<code>
receive
</code>
primitive to retrieve messages that match desired patterns. A message-handling routine tests messages in turn against each pattern, until one of them matches. When the message is consumed and removed from the mailbox the process resumes execution. A message may comprise any Erlang structure, including primitives (integers, floats, characters, atoms), tuples, lists, and functions.
</p>

</p>
<p>
Concurrency supports the primary method of error-handling in Erlang. When a process crashes, it neatly exits and sends a message to the controlling process which can then take action, such as starting a new process that takes over the old process's task.

<a>
<span>

</span>

<span>

</span>

</p>
<div>
<h2>
Implementation
</h2>
<span>
<span>
[
</span>
<a>
<span>
edit
</span>
</a>
<span>
]
</span>
</span>
</div>
<p>
The official
<a>
reference implementation
</a>
of Erlang uses
<a>
BEAM
</a>
.
<sup>
<a>
<span>
[
</span>
35
<span>
]
</span>
</a>
</sup>
BEAM is included in the official distribution of Erlang, called Erlang/OTP. BEAM executes
<a>
bytecode
</a>
which is converted to
<a>
threaded code
</a>
at load time. It also includes a native code compiler on most platforms, developed by the High Performance Erlang Project (HiPE) at
<a>
Uppsala University
</a>
. Since October 2001 the HiPE system is fully integrated in Ericsson's Open Source Erlang/OTP system.
<sup>
<a>
<span>
[
</span>
36
<span>
]
</span>
</a>
</sup>
It also supports interpreting, directly from source code via
<a>
abstract syntax tree
</a>
, via script as of R11B-5 release of Erlang.
</p>

</a>

<div>
<h2>
Distribution
</h2>
<span>
<span>
[
</span>
<a>
<span>
edit
</span>
</a>
<span>
]
</span>
</span>
</div>
<p>
In 1998, Ericsson released Erlang as
<a>
free and open-source software
</a>
to ensure its independence from a single vendor and to increase awareness of the language. Erlang, together with libraries and the real-time distributed database
<a>

</a>
, forms the OTP collection of libraries. Ericsson and a few other companies support Erlang commercially.
</p>
<p>
Since the open source release, Erlang has been used by several firms worldwide, including
<a>
Nortel
</a>
and
<a>
Deutsche Telekom
</a>
.
<sup>
<a>
<span>
[
</span>
37
<span>
]
</span>
</a>
</sup>
Although Erlang was designed to fill a niche and has remained an obscure language for most of its existence, its popularity is growing due to demand for concurrent services.
<sup>
<a>
<span>
[
</span>
38
<span>
]
</span>
</a>
</sup>
<sup>
<a>
<span>
[
</span>
39
<span>
]
</span>
</a>
</sup>
Erlang has found some use in fielding
<a>
massively multiplayer online role-playing game
</a>
(MMORPG) servers.
<sup>
<a>
<span>
[
